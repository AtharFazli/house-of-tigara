## 1. Product and users

**House of Tigara web ordering app** — a mobile-first pre-order webapp for a student-led F&B brand at Telkom University Jakarta, for Market Day (December 2026). Instagram: `@houseoftigara`.

Two user roles:

- **Buyer** (student or visitor): opens the page on a phone, picks one of three products, adds to cart, sends the order without an account, sees a confirmation. Wants speed and a page that "just works" on campus mobile.
- **Brand owner** (the team): receives the order list and changes order status. Wants a bare admin page, not a polished product yet (Phase 3).

This is a **task/commerce flow** used in public, on campus mobile, with an unstable signal, so scanability and resilience beat polish.

## 2. Brand and design

The brand is warm, artisanal, editorial, premium but approachable. Visual direction is in `design.md` (root) + `STYLE.md` (feed rules). For the web app:

- **Palette:** ivory/cream background, olive as primary brand color, terracotta as accent, beige for photo tiles. (Matches `design.md`: ivory `#fbf9f5`, olive `#273621`, terracotta `#94492e`, beige `#ddd5bd`.)
- **Type:** serif display (`Playfair Display`) for headlines + `Plus Jakarta Sans` for body/UI. Matches `design.md`.
- **Mode:** Operate (the visitor completes an order on a phone).

Display serif is explicitly required by the brief (R6 "huruf serif"), so the taste-skill's default-sans-serif rule is overridden by the brand brief — the brand names the serif.

## 3. Principles

- **Fast first:** a static Astro page that opens almost instantly on 4G (R5).
- **Fewest steps:** the buyer goes through no more than 4 steps, no account, no login.
- **Resilient:** cart survives signal loss via `localStorage`; order can be re-sent (R5).
- **No fakes:** no invented stock numbers, no fake-precise metrics, no AI-slop patterns (taste-skill §9 forbids: Inter default, AI-purple, three-equal-cards, em-dashes, generic names like "Acme"/"Jane Doe", wrapped CTAs, duplicate CTA intent, etc.).
- **One system per project:** use the tokens in `global.css` / `design.md`; do not mix in another design system.

## 4. Problem and solution

**Problem:** visitors wait passively for the stall; unstable campus signal; manual ordering queues drag out. Buyers lose patience and go elsewhere.

**Solution:** a static, fast landing + ordering surface. Buyer browses three products by photo and price, adds to cart (quantity control), enters name + WhatsApp contact, sends the order. Confirmation shows an order ID and pickup code. The cart is persisted to `localStorage` so it survives reload. Orders are written to a database (Supabase proposed) for the owner to read.

## 5. Success criteria (measurable)

- Buyer reaches confirmation with an order ID in **≤ 4 steps** from an open page.
- Mobile page opens within ~2 s on 4G; Lighthouse mobile Performance > 90; JS < 50 KB (proposal in PRD).
- All three products are visible on the menu with correct prices (Risol Mayo Rp 15.000, Coffee Bun Rp 12.000, Matcha Rp 16.000).
- Cart empty → submit button disabled; empty name/contact → inline error "Isi nama dan kontak dulu".
- Order ID is shown in confirmation; a pickup code is visible for the stall.
- Cart content survives page reload (localStorage) (R5).

## 6. Scope

**In scope (Phase 1 prototype):**
- Menu with 3 products + prices (R1).
- Add-to-cart + quantity change (R2).
- Checkout: name + contact, no account (R3).
- Order stored in DB (Supabase proposed) + read by owner (R4).
- Confirmation screen with order ID + pickup code (R7).
- Static fast page + localStorage cart (R5 partially — cart only).

**Out of scope now:**
- Payment gateway / QRIS wiring (R8) — placeholder "Bayar via Instagram DM".
- Owner admin page (list, password, status toggle) — Phase 3.

## 7. Technical constraints

- Framework: **Astro** (existing) — do not switch. Static `output: "static"`, server host enabled.
- Cart/form: vanilla JS inside Astro; no framework added.
- Cart persistence: `localStorage`, key `cart` → `[{ productId, quantity }]`.
- Order persistence: Supabase (proposed) — `products`, `orders`, `order_items` (schema in PRD §6). Currently a local stand-in in `cart.js` (`submitOrder` returns a fake `TIG-XXXX`); replace with real insert after backend approval.
- Hosting: static (Vercel proposed). No Node server needed for the buyer surface.
- No account, no login, no payment gateway, no points/vouchers, no multilanguage (PRD §2 constraints).

## 8. Risks and open questions

- `submitOrder` is a **local placeholder**; real send + retry ("Coba kirim lagi") is not implemented until Supabase is configured (R5 + R8).
- QRIS payment method (R8) is unresolved — needs a decision, not a code change.
- Admin password + status toggle are Phase 3 (owner) — not part of this prototype.
- `design.md` and `STYLE.md` use different font families (Playfair/Plus vs CaveatBrush/GARA); the web app follows `design.md` (Playfair + Plus Jakarta Sans). Feed-created images follow `STYLE.md`. Reconcile if the brand team requests otherwise.
- Server-side rendering is not used; `submitOrder`'s `fetch` to Supabase must be called from a client-side script or via a thin API route.
